Это подтверждает длительное ожидание API. Называть эти числа чистым временем SQL или CPU сервера пока нельзя: профилирование обработчика и запросов ещё не выполнено.

За исходный прогон браузер зарегистрировал четыре длительные задачи, максимальная — 84 мс, ошибок JavaScript нет. В этом сценарии многосекундная недоступность списков совпадает с ожиданием API; доказательств многосекундной блокировки основного потока браузера нет. Возможные затраты других экранов и фильтров этим не исключаются.

## 8.1.2. Профилирование и подтверждённые причины

**Статус: выполнен.** Основная задержка приходится на повторную обработку всего контекста расписания в JavaScript на сервере. Дополнительно подтверждены продолжение расчёта после клиентской отмены, блокировка других HTTP-запросов этим расчётом, широкий ответ применения и избыточно большой сохраняемый контекст операции. Изменения бизнес-логики и интерфейса на этом шаге не выполнялись.

### Методика и проверка самих измерений

Добавлен диагностический [scripts/profile-teacher-reassignments.mjs](../scripts/profile-teacher-reassignments.mjs). Он делает новую SQLite-копию, создаёт в `/tmp` снимок исходников с временными таймерами функций, считает вызовы и время `better-sqlite3`, затем вызывает настоящие обработчики Fastify через `app.inject`. Исходная база и продуктовые исходники не изменяются. Пробы входа и CSRF выполняются штатно в копии; значения параметров SQL, cookies и токены не записываются в результаты.

Использована `before-apply.sqlite` из 8.1.1: тот же школьный набор с 181 324 уроками и исходной версией 423. Хеши продуктовых файлов совпадают с предыдущим шагом. Новая копия — `/tmp/smena-replacements-profile-20261015-pld6yW/school.sqlite`. Все восемь вариантов предпросмотра сначала вызваны без таймеров функций, затем в инструментированном снимке; **JSON-ответы каждой пары побайтово совпали по SHA-256**. Отдельный CPU-профиль снят с исходной, не инструментированной функции. Проверки браузера выполнялись на исходной production-сборке и отдельном HTTP-сервере `127.0.0.1:3182`.

Таймеры дают накладные расходы: например, изменение строки четверти заняло 3,276 с без них и 4,098 с с ними. В таблицах фаз сравниваются части одного инструментированного запроса; эти числа не заменяют исходные пользовательские замеры. `app.inject` исключает TCP, но включает авторизацию, настоящий API, SQLite и сериализацию. SQL-время включает выполнение и материализацию возвращённых строк; подготовка выражений считается отдельно. Время родительской функции включает дочерние вызовы — такие значения нельзя складывать между собой.

### Почему выбор одной строки так дорог

| Повторяемая работа за один запрос | 23 выбранных урока | 47 выбранных уроков |
| --- | ---: | ---: |
| Уроков в прочитанном контексте всех групп | 16 602 | 18 382 |
| Полные разворачивания контекста (`locate`) | 1 203 | 2 403 |
| Проверки назначения (`mainReason`) | 529 | 1 081 |
| Повторные сборки списка занятий (`buildUnits`) | 28 | 52 |
| Копирования структуры расписания при подстановке (`updateLessons`) | 132 | 268 |
| Проверки принадлежности правилам (`unitMatchesStream`) | 381 846 | 863 954 |

В [shared/teacherReassignment.ts](../shared/teacherReassignment.ts) подтверждены следующие причины:

1. `mainReason` при каждой проверке снова разворачивает **весь** контекст через `locate`, находит участников урока, затем повторно разворачивает контекст для занятости. Для 23 уроков два полных прохода «11 кандидатов × 23 урока» и применение 23 выбранных назначений дают `253 + 253 + 23 = 529` проверок. Для 47 получается `517 + 517 + 47 = 1 081`.
2. Обобщённый список кандидатов считается в `assignPreview` до чтения индивидуальных целей и использует исходное расписание. При изменении только `unitTeacherIds` он пересчитывается заново, хотя его входные данные не менялись. Затем доступные преподаватели отдельно вычисляются для всех строк уже относительно пробного результата.
3. Подстановка очередного кандидата вызывает `updateLessons`, проходящий по структуре всех дней и ячеек. Это повторяется для каждого подходящего урока каждого кандидата, а затем ещё для применяемых назначений.
4. При сохранении назначения для повторной генерации `applyTeacher` для каждого успешного урока снова вызывает `buildUnits` по всей школе и фильтрует результат через `unitMatchesStream`. Только эта проверка потока вызывает 381 846 сравнений для 23 назначений. Правила можно строить пакетно для выбранных потоков, сохраняя их прежнюю семантику.

Для 23 уроков `locate` расходует 1 469 мс, собственная работа `buildUnits` — 1 016 мс, собственная работа `mainReason` без дочерних вызовов — 958 мс. Это около 84% всего инструментированного запроса. 1 203 полных разворачивания 16 602 уроков означают примерно 20 млн посещений уроков; для 47 — около 44 млн. Эти затраты объясняют рост времени даже при почти одинаковом SQL-времени.

Независимый CPU-профиль запроса на 47 уроков длительностью 7,323 с подтвердил преобладание `locate`, сборки единиц, преобразований занятости и фильтров. Сборщик мусора занял около 948 мс, примерно 13% времени этого профиля. Это согласуется с большим числом создаваемых массивов и объектов; величина относится к одному снятому профилю.

### Что показала проверка SQL и области данных

Основной запрос соединяет дни, ячейки и уроки. План для обоих диапазонов использует `schedule_days_date_group`, уникальный индекс ячеек по `day_id` и `lessons_slot_id`; для сортировки есть временное B-дерево. Измеренное выполнение основного чтения — 42 мс для четверти и 39 мс для бессрочного варианта. Текущие индексы используются; приоритет исправления — повторные обходы уже прочитанных данных.

Запрос передачи до конца четверти читает все 53 календарные даты диапазона и возвращает 16 602 урока. ## 8.1.4. Исправление подтверждённых причин

Реализовано 15.10.2026. Исходный код сохранён отдельно до изменений. Сравнение выполнено через настоящий API с авторизацией и CSRF на двух независимых online-backup копиях исходной базы: 181 324 урока, исходная версия 423. Рабочая база не использовалась для пробных записей. Запросы взяты из исходного браузерного сценария английского 10А; они совпадают по выбранным урокам, преподавателям и датам. Старый и новый сервер запускались последовательно в одном измерительном процессе; браузер измерялся отдельно, без параллельного нагрузочного прогона.

### Что изменено

- Контекст разворачивается в индекс уроков, участников совместных занятий, потоков и занятости по дате/преподавателю. Проверки списка выбранных уроков используют тот же индекс. Кандидаты моделируют изменения назначений через небольшой набор переопределений; расписание целиком больше не копируется для каждого кандидата и урока.
- Предпросмотр хранит одну актуальную область на сессию: исходные данные, индекс, общий список кандидатов и доступность строк. Ключ строки включает фактическую занятость в пересекающихся интервалах; выбор одной строки не запускает подбор для независимых строк. Смена области или версии черновика исключает старые результаты. Ограничение — три сессии, срок повторного использования 90 секунд, до 128 записей в каждой таблице результатов. Повтор идентичного запроса возвращает уже рассчитанный предпросмотр после проверки текущей версии и параметров.
- Быстрые изменения ввода объединяются за 60 мс. Индивидуальные списки остаются доступными при проверке строки; «Проверяем…» относится к изменённым и зависимым строкам. Применение ждёт актуального результата всего запроса. AbortController и проверка последовательности ответов сохранены.
- Применение заново читает базу и рассчитывает предложение, затем выполняет прежние независимые проверки расписания, недоступности, кабинетов и пересечений преподавателей. Данные других классов на затронутых датах по-прежнему участвуют в проверках.
- Запись обновляет только `teacher`/`teacher_ref` выбранных уроков, сохраняя соседние записи и физические идентификаторы ячеек. Новый снимок отмены содержит исходные поля преподавателя и даты выбранных уроков. При отмене снова загружаются все группы этих дат; исходные значения восстанавливаются точно. Старые журналы с полным расписанием поддерживаются.
- Страница запрашивает `response=receipt`: ответ содержит версию, время изменения и идентификатор применённой операции. Затем страница загружает своё актуальное представление обычным API. Ответы без этого параметра и прежний `response=compact` совместимы с существующими клиентами. Повтор записи с тем же идентификатором возвращает сохранённый ответ, не создавая новую операцию.

## 8.1.5. Техническая проверка матрицы и подготовка визуальной приёмки

Проверка от 15.10.2026 выполнена на новых online-backup копиях текущей базы: **181 324 урока, 74 группы, 131 преподаватель, исходная версия 423**. Для серверных ограничений добавлены небольшие управляемые примеры поверх большой копии; для ошибок интерфейса — один недоступный интервал заменяющего и два разных периода отсутствия. Они существуют только в QA-копиях. Замеры скорости выполнены на отдельной копии исходных данных без этих примеров. Рабочие данные не использовались для пробных записей или публикации.

### Найденные ошибки и исправления

1. Запрос одного/нескольких уроков с `scope=lesson` и `lessonIds`, без одиночного `lessonId`, принимался контрактом, но сервер не находил даты, а расчёт дополнительно отфильтровывал все уроки. Исправлены загрузка дат и выбор единиц. Выбор одного участника совместного занятия сохраняет общий урок целиком. Добавлены узкие регрессионные проверки.
2. Бессрочный период с группой и предметом, без исходного преподавателя и списка уроков, возвращал пустой результат. Теперь исходные потоки определяются по занятиям выбранной группы/предмета в текущей четверти; на найденных датах по-прежнему загружаются все группы для проверки занятости. Явные идентификаторы уроков и фильтр преподавателя сохраняют прежний смысл.
3. После потери связи при записи кнопка «Применить» снова становилась доступной, хотя исходный запрос ещё мог быть выполнен. Кроме того, явный отказ HTTP 400 при повторе очищал запрос, но оставлял признак неизвестного результата: диалог нельзя было закрыть, а повтор уже ничего не отправлял. Теперь новый запуск заблокирован и в кнопке, и в обработчике до выяснения результата; повтор использует исходный идентификатор. Явный отказ освобождает диалог. Обе ошибки воспроизведены в браузере до исправления и проверены теми же действиями после него.

Также уточнён статус явно пропущенной строки: **«Оставлено без изменений»** вместо «Ожидает выбора». Смысл применения и подтверждения частичного результата не менялся.
